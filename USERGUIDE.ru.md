# SelfReview: руководство пользователя

[English](USERGUIDE.md) · [README](README.md) · [Справочник правил](docs/RULES.md)

SelfReview — локальный инструмент для подготовки к ревью JS/TS-кода. Он хранит договорённости по скоупам, собирает кандидатов из кода, документов и замечаний к MR, выполняет ограниченный набор AST-проверок и формирует материалы для агента или человека.

Главный рабочий цикл: **собрать источники → посмотреть кандидатов → подтвердить применимые договорённости → проверять изменения → разобрать семантику с человеком или агентом**. Часто встречающийся код и закрытый комментарий к MR сами по себе не становятся обязательными правилами.

## 1. Что нужно для запуска

Для Git-режимов нужна поддержка `git --no-lazy-fetch`. Проверить её можно командой
`git --no-lazy-fetch --version`. Недостающие Git-объекты приводят к явной ошибке,
без загрузки из promisor remote. Проверка текущих исходников без Git остаётся доступной.

Нужны **Node.js 22.13 или выше**, npm и Git для клонирования репозитория и режима `--base`. В Git-репозитории нет `node_modules`: после клонирования нужно установить зависимости из lockfile.

Примеры ниже рассчитаны на Windows PowerShell 5.1. Команды идут отдельными строками; `npm.cmd` позволяет вызывать npm без изменения политики выполнения PowerShell. Не используйте в PowerShell 5.1 оператор `&&`.

```powershell
node --version
git clone https://github.com/levencode-labs/selfreview.git 'C:\SelfReview'
Set-Location 'C:\SelfReview'
npm.cmd ci --ignore-scripts
node .\bin\selfreview.mjs --version
node .\bin\selfreview.mjs --help
```

`npm.cmd ci --ignore-scripts` устанавливает runtime- и dev dependencies. Если нужен только CLI, вместо полной установки можно выполнить:

```powershell
npm.cmd ci --ignore-scripts --omit=dev
```

Для тестов и проверки ESLint-адаптера нужны dev dependencies — используйте полную команду без `--omit=dev`. `npm ci` может обращаться к настроенному npm registry. Рабочие команды CLI после установки не требуют сети, токена или AI API.

В Linux/macOS эквивалент начала работы:

```sh
git clone https://github.com/levencode-labs/selfreview.git
cd selfreview
npm ci --ignore-scripts
node bin/selfreview.mjs --help
```

Дальнейшие команды предполагают, что SelfReview находится в `C:\SelfReview`, а проверяемые проекты — в `C:\Repos\A` … `C:\Repos\E`. Запускайте их из корня SelfReview; для путей с пробелами сохраняйте кавычки. Переменная `$srConfig` действует только в текущей сессии PowerShell: задайте её заново в новом окне. В Linux/macOS замените Windows-пути своими и используйте `node bin/selfreview.mjs`.

Проверки реализации выполнялись в Linux на Node.js 24.22.1. PowerShell-примеры проверены по синтаксису; полный ручной прогон всех примеров на Windows PowerShell 5.1 не выполнялся. Автоматические Windows-прогоны и исправление проверки корня Git описаны в [CI follow-up](verification/GITHUB_CI.md). CLI help, часть диагностических сообщений и экспортируемые пояснения сейчас написаны по-русски. Справочник `docs/RULES.md`, архитектурные заметки `docs/ARCHITECTURE.md` и отчёт `VERIFICATION.md` также остаются русскоязычными. Полная локализация интерфейса не заявляется; имена команд и JSON-полей не зависят от языка руководства.

## 2. Создать три скоупа: A, B/C/D и E

Хранить конфигурацию можно отдельно от проверяемых репозиториев. Это удобно, когда одна система договорённостей относится к нескольким проектам.

```powershell
$srConfig = 'C:\SelfReview\workspace\selfreview.config.json'

node .\bin\selfreview.mjs init --config $srConfig --scope a --project 'C:\Repos\A'

node .\bin\selfreview.mjs scope add team-bcd --config $srConfig --project 'C:\Repos\B' --project 'C:\Repos\C' --project 'C:\Repos\D'

node .\bin\selfreview.mjs scope add e --config $srConfig --project 'C:\Repos\E'

node .\bin\selfreview.mjs doctor --config $srConfig
```

Папки проектов должны уже существовать. `init` создаёт конфигурацию и пустой каталог правил; код проекта не изменяется. Команда откажется перезаписать существующую конфигурацию или каталог.

Для папок с именами A, B, C, D, E автоматически получатся project ID `a`, `b`, `c`, `d`, `e`. Scope ID и project ID — разные поля: у проектов `b`, `c`, `d` будет общий scope `team-bcd`. При совпадении имён папок программа добавляет суффикс к project ID; точные идентификаторы видны в ответах `init`, `scope add` и `doctor`.

| Scope | Проекты | Общие правила |
|---|---|---|
| `a` | `a` | Договорённости проекта A |
| `team-bcd` | `b`, `c`, `d` | Общая база команды B/C/D |
| `e` | `e` | Договорённости проекта E |

Один проект назначается одному скоупу. Правила другого скоупа не подключаются из-за похожего имени папки. Для наследования нужно явно указать `extends`; для разных правил внутри одного проекта используйте `applicability`, описанную в [справочнике правил](docs/RULES.md).

В `init` и `scope add` параметр `--project` принимает **папку**; в `review`, `agent-pack` и `export` — зарегистрированный **project ID**. Корни проектов не могут пересекаться как родительская и вложенная папки. Для создания наследующего скоупа доступна форма `scope add NAME --extends PARENT --project FOLDER`: родитель уже должен существовать. Чтобы изменить наследование существующего скоупа, отредактируйте и проверьте конфигурацию.

После этих команд основные файлы расположены здесь:

- `C:\SelfReview\workspace\selfreview.config.json` — проекты, скоупы и настройки.
- `C:\SelfReview\workspace\.selfreview\catalog.json` — кандидаты, подтверждённые правила, источники и решения.

Каталог является обычным локальным JSON. Он может содержать цитаты из внутренних документов и MR. Инструмент не добавляет записи в `.gitignore` ваших проектов. Если переносите конфигурацию внутрь репозитория, самостоятельно определите, какие файлы допустимо версионировать, и добавьте нужные исключения.

`doctor` проверяет конфигурацию и каталог. Он не проверяет весь код и не доказывает отсутствие конфликтов применимости: для этого нужен `review`.

## 3. Наполнить scope из папок, документов и MR

Например, договорённости A лежат в `C:\Rules\A`, а выгрузка замечаний — в `C:\Reviews\review.json`:

```powershell
node .\bin\selfreview.mjs learn --config $srConfig --scope a --docs 'C:\Rules\A' --mr 'C:\Reviews\review.json' --out 'C:\SelfReview\workspace\learn-a.json'
```

Эта команда читает код проектов, непосредственно назначенных scope `a`, документы в указанной папке и замечания к MR. Результат — JSON-отчёт и новые **кандидаты** в каталоге. У `learn` нет отдельного текстового представления: отчёт записывается в JSON и при настройках вывода по умолчанию.

Поддерживаемые документы: UTF-8 Markdown, обычный текст и JSON с декларативными правилами. DOCX, PDF, HTML-страницы и изображения напрямую не разбираются. Их содержимое можно предварительно сохранить как Markdown или текст. О неподдержанных файлах в папке будет указано в предупреждениях.

Параметры `--docs` и `--mr` можно повторять:

```powershell
node .\bin\selfreview.mjs learn --config $srConfig --scope team-bcd --docs 'C:\Rules\Shared' --docs 'C:\Rules\Testing.md' --mr 'C:\Reviews\first.json' --mr 'C:\Reviews\second.json' --out 'C:\SelfReview\workspace\learn-team.json'
```

Код анализируется по умолчанию. `--code` сужает выборку до явно указанных папок или файлов внутри проектов выбранного scope. Он не меняет назначение проектов и не делает эту выборку представительной автоматически:

```powershell
node .\bin\selfreview.mjs learn --config $srConfig --scope a --code 'C:\Repos\A\src\components' --docs 'C:\Rules\A' --out 'C:\SelfReview\workspace\learn-components.json'
```

Для импорта только документов и замечаний:

```powershell
node .\bin\selfreview.mjs learn --config $srConfig --scope a --no-code --docs 'C:\Rules\A' --mr 'C:\Reviews\review.json' --out 'C:\SelfReview\workspace\learn-sources.json'
```

### Точное правило через JSON

Когда договорённость имеет исключения или несколько вариантов, задавайте параметры явно. Например, сохраните `C:\Rules\A\logging.json`:

```json
{
  "title": "Логирование приложения",
  "description": "В исходниках приложения разрешены только console.warn и console.error; штатное логирование идёт через logger.",
  "family": "no-console",
  "mode": "enforce",
  "severity": "error",
  "check": {
    "kind": "no-console",
    "options": { "allowMethods": ["warn", "error"] }
  },
  "applicability": {
    "include": ["src/**/*.ts", "src/**/*.tsx"],
    "exclude": ["**/*.test.ts", "**/*.test.tsx"]
  }
}
```

```powershell
node .\bin\selfreview.mjs learn --config $srConfig --scope a --no-code --docs 'C:\Rules\A\logging.json' --out 'C:\SelfReview\workspace\learn-logging.json'
```

Импорт поддерживает один объект, массив объектов или объект с массивом `rules`. Тот же JSON можно поместить в Markdown-блок с точным языком `selfreview-rule`. Импортёр назначает scope из команды, создаёт ID и реальные сведения об источнике; даже переданный `status: approved` не обходит состояние кандидата.

Пути `applicability` относительны корню каждого проекта выбранного scope. Поддерживаются `*`, `**`, `?`; перечисляйте альтернативы отдельными строками массива, без конструкции `*.{ts,tsx}`. Для вариантов одной семьи используйте непересекающиеся пути либо явные `overrides` и `overrideReason`. Укажите точные ID проверенных правил, которые заменяете; одного порядка записей в JSON недостаточно. Семья и область действия влияют на конфликты, поэтому проверьте их перед подтверждением. Полные примеры наследования, вариантов и ручных исключений — в [справочнике правил](docs/RULES.md).

### Что действительно извлекается автоматически

Статический discovery этой версии рассматривает три семейства:

- использование `const`/`let` вместо `var`;
- строгие сравнения, включая отдельный вариант с разрешённым `== null`;
- фигурные скобки у поддерживаемых управляющих конструкций.

Пороги по умолчанию: как минимум пять наблюдений и доля 0,9. Это число синтаксических наблюдений, а не пять независимых проектов или ревьюеров. `--min-samples` и `--threshold` меняют отбор кандидатов, но не подтверждают их. Размеры функций, компонентов и число параметров могут использоваться как статистика выборки; автоматически полученный p95 не объявляется договорённостью команды.

Для общего scope отчёт содержит агрегированные наблюдения и профили отдельных проектов. Если проект с достаточным числом наблюдений противоречит общему кандидату, такой кандидат удерживается с причиной `MIXED_PROJECT_CONVENTIONS`. Большой проект не должен незаметно сделать свой стиль обязательным для соседнего. Малая выборка сама по себе также не доказывает согласованность.

Из текста распознаются узкие формулировки вроде «Не использовать var», «Do not use console except warn, error», «Components must have at most 100 lines». Произвольная формулировка сохраняется как кандидат `manual`. Для точной машинной интерпретации используйте JSON или блок `selfreview-rule` из [RULES.md](docs/RULES.md).

Контекст Markdown-заголовков сохраняется вместе с предложением. Нейтральные заголовки вроде `Agreements` и `Variables` поддерживаются; заголовок `Production code only`, `Только production`, `tests/**`, `for legacy` или иной неоднозначный контекст оставляет текстовое правило в `manual`. Пути из такого заголовка не угадываются. Структурированное правило с явно заданной `applicability` может остаться AST-кандидатом, но требует проверки связи между параметрами и текстовыми условиями.

Импорт воспринимает текст документов и комментариев как данные. Указания «запусти команду», «подтверди все правила» или похожие фразы в источнике не выполняются и не становятся решением пользователя.

Смотрите `warnings`, `unmapped`, `codeFilesAnalyzed` и сведения о покрытии. Статус `CANDIDATES_READY` означает завершение поддерживаемого импорта; он не означает полноту описания всех соглашений проекта. Ошибка чтения, неподдержанный документ или неполный разбор могут дать `CANDIDATES_WITH_COVERAGE_GAPS`. `learn` может завершиться с кодом 0 и таким статусом: проверяйте JSON-поля покрытия, а не только код процесса.

## 4. Посмотреть и подтвердить одно правило

Сначала получите список:

```powershell
node .\bin\selfreview.mjs rules list --config $srConfig --scope a
```

Идентификатор кандидата зависит от его содержимого и источника. Не подставляйте выдуманный ID из чужого примера и не подтверждайте весь список по признаку высокой частоты. Скопируйте точный ID одного правила из своего вывода:

```powershell
$srRuleId = Read-Host 'Вставьте точный id одного кандидата из rules list'
node .\bin\selfreview.mjs rules show $srRuleId --config $srConfig
```

Перед подтверждением проверьте:

1. Соответствует ли формулировка реальному соглашению, а не частному замечанию к одному месту.
2. Правильно ли указаны scope и пути `include`/`exclude`.
3. Сохранены ли исключения и параметры, например `allowNull` или разрешённые методы `console`.
4. Достаточно ли источника и контекста MR; не устарел ли совет.
5. Не пересекается ли правило с другим вариантом той же семьи.

После содержательного решения:

```powershell
node .\bin\selfreview.mjs rules approve $srRuleId --config $srConfig --by 'Developer' --reason 'Проверил действующую договорённость команды и область применения'
```

Или отклоните неподходящего кандидата, сохранив причину:

```powershell
node .\bin\selfreview.mjs rules reject $srRuleId --config $srConfig --by 'Developer' --reason 'Это локальное замечание к одному MR, а не правило всего scope'
```

`--by` — запись о принятом решении, а не криптографическая подпись или проверка полномочий человека. Правильность подтверждения остаётся ответственностью пользователя.

Для машинной обработки списка используйте JSON:

```powershell
node .\bin\selfreview.mjs rules list --config $srConfig --scope a --json --out 'C:\SelfReview\workspace\rules-a.json'
$srRules = Get-Content 'C:\SelfReview\workspace\rules-a.json' -Raw -Encoding UTF8 | ConvertFrom-Json
$srRules | Select-Object id, status, title
```

### Редактирование и повторное обучение

Можно отредактировать `catalog.json` локальным редактором. Изменение проверяемого содержания подтверждённого правила — параметров, применимости, формулировки или источников — делает прежнее подтверждение недействительным. Проверка остановится с `STALE_APPROVAL`, пока новая версия не просмотрена и не подтверждена заново. Не пересчитывайте вручную `approval.behaviorHash`.

Повторные эквивалентные свидетельства накапливаются вокруг устойчивого идентификатора правила. Посторонний абзац в документе не создаёт неизменившуюся договорённость заново. Изменение условий, параметров, скоупа или применимости создаёт отдельного кандидата с возможной связью с предыдущей версией. Подтверждённые и отклонённые снимки не перезаписываются. Неоднозначные формулировки остаются раздельными. Сравните версии и явно выберите актуальную, чтобы два активных пересекающихся правила не конфликтовали. История, предварительная проверка и обновление источников описаны в разделе 11.

## 5. Как передать MR

### Нейтральный JSON

Сохраните UTF-8 файл `C:\Reviews\review.json`:

```json
{
  "title": "Пример MR с обсуждением логирования",
  "diff": "--- a/src/format.ts\n+++ b/src/format.ts\n@@ -1 +1 @@\n-console.log(value);\n+logger.info(value);\n",
  "comments": [
    {
      "body": "Do not use console.",
      "path": "src/format.ts",
      "line": 1,
      "side": "old",
      "resolved": true
    },
    {
      "body": "В этом адаптере важно сохранить порядок побочных эффектов.",
      "path": "src/format.ts",
      "line": 1,
      "side": "new",
      "resolved": false
    }
  ]
}
```

Первая запись станет кандидатом на машинную проверку; вторая — пунктом `manual`. `resolved: true` сохраняет состояние обсуждения, но не подтверждает универсальную конвенцию. Сторона старого кода не подменяется новой строкой.

### Diff и комментарии отдельными файлами

В `comments.json` может находиться массив комментариев с `body`, `path`, `line`, `side`, `resolved`:

```powershell
node .\bin\selfreview.mjs learn --config $srConfig --scope a --no-code --diff 'C:\Reviews\change.diff' --comments 'C:\Reviews\comments.json' --out 'C:\SelfReview\workspace\learn-mr.json'
```

Для парного импорта нужны оба параметра: `--diff` и `--comments`. Также можно передать обычный текст комментариев. Тогда связь с конкретными строками будет слабее и сохранится как непроверенный контекст. Diff без замечаний импортируется как контекст; по самому факту замены кода новое командное правило не выводится. Для такого источника можно передать через `--mr` JSON с `diff` и пустым массивом `comments`, не пропуская обязательный параметр в парной форме.

### Выгрузка GitLab discussions

Поддерживаются массивы discussions с `notes`, например:

```json
[
  {
    "id": "discussion-example",
    "notes": [
      {
        "id": 123,
        "body": "Не использовать var.",
        "system": false,
        "resolved": true,
        "author": { "username": "reviewer" },
        "position": {
          "old_path": "src/example.ts",
          "new_path": "src/example.ts",
          "old_line": 12,
          "new_line": null
        }
      }
    ]
  }
]
```

Передайте этот файл через `--mr`. Системные заметки GitLab не становятся правилами. Прямое подключение к GitLab, загрузка MR по URL и получение токена в эту версию не входят.

## 6. Проверять код перед отправкой MR

### Весь проект или все проекты скоупа

```powershell
node .\bin\selfreview.mjs review --config $srConfig --project a

node .\bin\selfreview.mjs review --config $srConfig --scope team-bcd --format json --out 'C:\SelfReview\workspace\review-team.json'
```

Проект A использует scope `a`, а проекты B/C/D — общий scope `team-bcd`. Для конкретного файла дополнительно проверяется применимость каждого правила. Перекрывающиеся варианты одной семьи требуют явного решения; порядок записей в JSON не определяет победителя.

### Только изменения относительно локального Git ref

Если `C:\Repos\A` — точный корень Git-репозитория:

```powershell
node .\bin\selfreview.mjs review --config $srConfig --project a --base origin/main --format json --out 'C:\SelfReview\workspace\review-a.json'
$srReviewExit = $LASTEXITCODE
```

`origin/main` должен уже существовать локально. Команда не выполняет `fetch`. Сравнение идёт с указанным commit/ref, а не с автоматически вычисленным merge base. При `--base HEAD` рассматриваются локальные изменения относительно HEAD; при другом ref в сравнение войдёт соответствующая разница с текущим рабочим деревом. Новые неотслеживаемые файлы учитываются отдельно.

Конфигурация проекта должна указывать на сам Git root. Инструмент откажется читать Git-метаданные родительского репозитория, если назначенный project root — лишь вложенная папка. Для монорепозитория с таким режимом зарегистрируйте один Git root и задайте варианты правил через пути.

### Готовый diff

```powershell
node .\bin\selfreview.mjs review --config $srConfig --project a --diff 'C:\Reviews\current.diff' --format json --out 'C:\SelfReview\workspace\review-diff.json'
```

Пути в diff должны быть относительны корню выбранного проекта, а новые и контекстные строки — соответствовать текущим файлам. Устаревший контекст приводит к неполной проверке. Произвольный deletion-only diff с `-U0` не содержит строк новой версии, по которым можно проверить его соответствие; используйте свежий `--base` или diff с контекстом.

Проверяется полный AST файла, затем результаты фильтруются по пересечению с затронутыми узлами. Поэтому добавление строки в большой компонент может вызвать находку, даже если объявление компонента находится вне diff. Такая находка **затрагивает изменение**, но не доказана как впервые внесённая ошибка: для строгой атрибуции регрессии нужен анализ базовой версии.

### Как читать результат

| Статус | Что означает | Код завершения |
|---|---|---:|
| `CHECKS_PASSED` | Выбранные исполняемые проверки завершены без блокирующих находок | 0 |
| `VIOLATIONS` | Найдены нарушения подтверждённых `enforce`-правил с уровнем `error` | 1 |
| `INCOMPLETE` | Нельзя честно завершить проверку: конфигурация, конфликт, разбор, входные данные или покрытие | 2 |
| `ADVISORY_ONLY` | Выполнены только неблокирующие рекомендации; обязательных AST-проверок нет | 0 |
| `MANUAL_REVIEW_REQUIRED` | В применимых подтверждённых правилах остаются ручные пункты | 0 |
| `NO_CHANGES` | Переданный diff не содержит изменений для этого запуска | 0 |
| `NOT_APPLICABLE` | В изменении нет применимых JS/TS-файлов новой версии, например изменён только README или файлы удалены | 0 |

Для нескольких проектов JSON содержит массив `reports` и общий `exitCode` — максимальный код из отчётов. Ошибки, возникшие до создания отчёта, могут записываться в stderr с кодом 2.

Нулевой exit code не равен одобрению всего MR. Если CI требует закрытого ручного ревью, отдельно учитывайте `status` и `manualChecklist`. `build`, проверка типов, существующие тесты, runtime и оценка бизнес-логики остаются самостоятельными проверками.

Текстовый отчёт группирует повторяющиеся рекомендации и показывает не более трёх примеров в группе; JSON сохраняет полный список находок.

Для сохранения отчёта используйте `--out`: инструмент сам записывает UTF-8. Это удобнее, чем полагаться на настройки перенаправления вывода PowerShell.

## 7. Использовать агента перед кодом и после него

Соберите пакет для выбранного проекта:

```powershell
node .\bin\selfreview.mjs agent-pack --config $srConfig --project a --base origin/main --out 'C:\SelfReview\workspace\agent-pack-a.json'
```

`agent-pack` возвращает код вложенной проверки. Файл может быть успешно записан и при коде 1 из-за найденных нарушений; прочитайте отчёт внутри него.

Пакет содержит выбранные project/scope, текущие правила, кандидатов-вопросы, AST-отчёт и контракт ответа. Команда сама не запускает LLM, сабагента или API. Её код завершения отражает результат вложенной проверки, поэтому файл может быть создан и при найденных нарушениях.

Практический запрос агенту:

> Используй этот SelfReview agent-pack для проекта a. Сначала проверь актуальные конфигурацию, каталог и применимость правил. Перед реализацией опиши ответственности и побочные эффекты. После изменений выполни SelfReview и требуемые проектом проверки, затем отдельно проверь обработку ошибок, владение состоянием, декомпозицию и поведение. Кандидатов не подтверждай автоматически. В ответе раздели нарушения договорённостей, рекомендации и непроверенные вопросы.

В отдельном ревью полезно смотреть на изменённые функции целиком: короткий компонент тоже может смешивать ответственности, а длинный иногда остаётся обоснованным. Счётчик строк — повод проверить устройство кода.

Если агент предложил дополнительные соглашения, сохраните их как декларативный JSON и импортируйте:

```powershell
node .\bin\selfreview.mjs learn --config $srConfig --scope a --no-code --proposals 'C:\SelfReview\workspace\proposed-rules.json' --out 'C:\SelfReview\workspace\learn-proposals.json'
```

Предложения снова проходят состояние `candidate`. Запускать сгенерированный произвольный JavaScript как правило этот механизм не позволяет: исполняемые `kind` и параметры ограничены схемой ядра.

## 8. Экспортировать Skill, справочник и ESLint

```powershell
node .\bin\selfreview.mjs export --config $srConfig --scope a --project a --out 'C:\SelfReview\exports\a-v1'
```

Папка назначения должна отсутствовать или быть пустой. Для повторного экспорта выберите новую папку, например `a-v2`.

| Файл | Назначение |
|---|---|
| `rules.json` | Снимок подтверждённых правил и настроенного рекомендательного слоя |
| `candidates.json` | Отдельный список неподтверждённых кандидатов |
| `CONVENTIONS.md` | Человекочитаемый справочник с источниками |
| `selfreview-a/SKILL.md` и `references/` | Инструкции для агента и снимок подтверждённых правил |
| `eslint.config.mjs` | Адаптер выбранного проекта к тому же AST-ядру |
| `export-coverage.json` | Сведения о включённых проверках и ограничениях экспорта |

Skill — экспортированный артефакт. Команда не устанавливает его в Codex или ChatGPT и не доказывает, что агент будет безошибочно следовать ему. Снимок может устареть; перед изменениями нужны актуальный локальный каталог и свежий отчёт.

ESLint-конфигурация содержит локальную ссылку на адаптер SelfReview и путь к конфигурации. После перемещения SelfReview или конфигурации экспортируйте её заново. Если scope содержит B/C/D, создавайте экспорт для конкретного проекта через `--project b`, `--project c` или `--project d`. Без `--project` выбирается первый проект, непосредственно назначенный скоупу; это может быть не тот проект, который вы собирались проверять.

ESLint остаётся инструментом принимающего проекта. Для TS/TSX нужен его TypeScript-aware parser; обычный CLI SelfReview уже разбирает TS/TSX самостоятельно. Пример подключения через существующий конфигурационный файл проекта:

```javascript
import tsParser from '@typescript-eslint/parser';
import { createFlatConfig } from 'file:///C:/SelfReview/src/eslint.mjs';

const selfreviewConfig = createFlatConfig(
  'C:/SelfReview/workspace/selfreview.config.json',
  'a',
);

export default selfreviewConfig.map(config => ({
  ...config,
  languageOptions: {
    ...config.languageOptions,
    parser: tsParser,
  },
}));
```

В существующем проекте включите этот массив в свою конфигурацию, сохранив её другие проверки. Пример показывает интеграцию, а не команду перезаписать действующий ESLint setup. Установленный parser должен быть совместим с версией ESLint проекта. Версии зависимостей для разработки самого SelfReview зафиксированы в `package-lock.json`; они не устанавливают parser в проверяемый проект.

В адаптере советы отображаются как `warn`. Поэтому внешняя политика ESLint `--max-warnings=0` способна сделать их блокирующими, хотя CLI SelfReview не считает их обязательными ошибками. Это решение конфигурации принимающего проекта.

ESLint анализирует только переданные ему файлы. Для инвентаризации покрытия, проверки diff и ручного checklist используйте CLI SelfReview. Не отключайте проверки целостности адаптера; после изменения загруженной конфигурации или каталога перезапускайте долгоживущий процесс ESLint.

## 9. Настроить best practices

По умолчанию включён рекомендательный слой: `var`, нестрогие сравнения, большие функции/компоненты, число параметров, async executor `Promise`, некоторые потенциально устаревшие вызовы. Эти находки имеют `mode: advisory` и `severity: info` в CLI.

Подтверждённая конвенция того же семейства или вида проверки имеет приоритет. Для локального исключения используйте применимое подтверждённое `manual`-правило; пример сохранения legacy API есть в [RULES.md](docs/RULES.md).

Для полного выключения рекомендаций установите в конфигурации:

```json
"bestPractices": false
```

Для выключения отдельного совета в одном скоупе добавьте в его `disabledRules` ID и содержательную причину:

```json
{
  "id": "e",
  "extends": [],
  "disabledRules": [
    {
      "id": "bp.legacy-calls",
      "reason": "Legacy runtime: допустимость замены API проверяется вручную по совместимости"
    }
  ]
}
```

Тот же механизм может отключить конкретное подтверждённое правило каталога. Это явное изменение конфигурации; оно должно соответствовать реальному соглашению команды.

## 10. Границы версии и проверка самого инструмента

Поддерживаемые исходники: `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.mts`, `.cts`. React-компоненты распознаются эвристически по AST; полная семантика React и граф импортов не доказываются. Declaration files исключаются. Для `.NET`/C#, Vue SFC, Svelte и других языков нужны отдельные адаптеры; эта версия не заявляет их проверку.

В поставке нет desktop UI, прямого клиента GitLab, автоматического запуска агента и доказательства полноты правил по любому коду. Общее правило хранится как данные, а CLI, ESLint и Skill используют разные способы его применения. Неисполняемая договорённость остаётся ручным пунктом.

Сам CLI не выполняет сетевых запросов и не запускает проверяемый код. Установка зависимостей через npm и дальнейшая передача пакета облачному агенту — отдельные действия пользователя. Экспорты и agent-pack могут содержать имена проектов, пути и цитаты из исходных документов или MR; учитывайте это перед передачей файла кому-либо.

Для разработки и повторного запуска тестов нужны dev dependencies из lockfile. В PowerShell 5.1 можно использовать `npm.cmd`, чтобы не менять политику выполнения скриптов:

```powershell
Set-Location 'C:\SelfReview'
npm.cmd ci --ignore-scripts
npm.cmd test
```

После клонирования установка зависимостей обязательна. Если ранее использовали `--omit=dev`, повторный `npm.cmd ci --ignore-scripts` добавит зависимости для тестов. Наличие Linux-тестов не заменяет нативную приёмку на вашем Windows toolchain.

## 11. Поддерживать правила и готовить ежедневную задачу

### История и предварительная проверка

Используйте идентификатор из `rules list`:

```powershell
node .\bin\selfreview.mjs rules history $srRuleId --config $srConfig
node .\bin\selfreview.mjs rules preview $srRuleId --config $srConfig --project a
```

История показывает свидетельства, источники, возможные версии и записанные
решения. Предварительная проверка временно активирует выбранного кандидата в
отдельной копии каталога в памяти. Она показывает применимые файлы, находки,
конфликты, ручные вопросы и примеры. Каталог на диске и решения не изменяются;
находки preview не становятся действующей политикой.

Новые одинаковые замечания добавляются к наблюдениям, сохраняя утверждённый или
отклонённый снимок. Отличающиеся скоупы, условия, параметры и исключения остаются
разными правилами. Связь между версиями означает предложение для пересмотра.

### Обновить зарегистрированные источники

```powershell
node .\bin\selfreview.mjs sources status --config $srConfig --scope a
node .\bin\selfreview.mjs sources refresh --config $srConfig --scope a
```

`status` читает текущие файлы без записи и различает `current`, `changed`,
`missing`, `unavailable`. `refresh` повторно импортирует зарегистрированные
документы, выгрузки MR, предложения и пары comments/diff. Он не запускает новое
сканирование кода и не подтверждает либо отклоняет правила. Недоступные,
отсутствующие и неподдерживаемые источники остаются пробелами покрытия; код
завершения такого обновления — 2.

Реестр хранит импортированные файлы. Для обнаружения новых файлов в папке
повторите `learn --docs ПАПКА`. Старые свидетельства без зарегистрированного,
однозначно разрешимого источника отмечаются отдельно.

Если пункт исчез из обновлённого документа, прежнее утверждённое правило
сохраняется с указанием `SOURCE_RULE_NOT_REOBSERVED`. Его нужно пересмотреть
явно. Совпадение текущего хеша документа не означает повторного подтверждения
каждого старого пункта.

Автообнаружение показывает для каждого проекта состояния `supported`,
`contradicted`, `insufficient`, `unobserved`. Малая выборка и отсутствие
наблюдений не считаются подтверждением общего соглашения.

### Подготовить контекст конкретных файлов для агента

```powershell
node .\bin\selfreview.mjs context --config $srConfig --project a --file src/Panel.tsx --file src/new-helper.ts --out 'C:\SelfReview\workspace\task-context-a.json'
node .\bin\selfreview.mjs context check --config $srConfig --input 'C:\SelfReview\workspace\task-context-a.json'
```

Повторяемый `--file` принимает путь относительно корня зарегистрированного
проекта. Можно указать будущий файл. Без `--file` используется настроенный набор
файлов проекта. Правила разрешаются отдельно для каждого файла; отключённые и
переопределённые варианты находятся в `suppressed`, кандидаты остаются вопросами.
Ручные пункты содержат файлы и ожидаемый характер ответа. В контексте есть
абсолютные локальные пути и готовые массивы аргументов запуска проверок.

Проверка актуальности возвращает `CONTEXT_CURRENT`, `STALE_CONTEXT` либо
`INCOMPLETE`. Сверяются действующие конфигурация, каталог, байты выбранных файлов
и источники унаследованных соглашений. Самостоятельный пересчёт хеша пакета не
делает выдуманные правила соответствующими каталогу. Это проверка согласованности,
а не электронная подпись или аутентификация.

Проверяйте актуальность **перед редактированием**. Изменение выбранного файла
закономерно делает прежний снимок устаревшим. После правок запустите свежую
проверку и обязательные проверки проекта; для следующего шага сформируйте новый
контекст. `agent-pack` теперь содержит этот контекст вместе с отчётом. При проверке
сохранённого пакета `context check` дополнительно сверяет политику, источники и
метаданные снимка Git, включая изменение индекса без изменения рабочего файла.
Сами находки заново не вычисляются; происхождение отчёта не аутентифицируется. Отчёт по
staged-снимку может отличаться от рабочего дерева: смотрите `reportBinding` и
метаданные снимка в отчёте.

### Добавить проверяемые примеры

В декларативном правиле можно задать:

```json
"examples": [
  { "filename": "example.ts", "code": "const count = 1;", "expect": "valid" },
  { "filename": "example.ts", "code": "var count = 1;", "expect": "violation" }
]
```

Примеры разбираются тем же AST-checker без выполнения кода. Ожидание относится
к отдельной проверке; применимость по проектам и путям разрешается отдельно.
Неверное ожидание, ошибка разбора и некорректный формат видны в результате.
Ручные и старые произвольные примеры остаются непроверенными. В качестве
проверенных иллюстраций используйте только `PASS`. Ограничения: 50 примеров,
до 32 КиБ кода в каждом.

### Отделить новые находки от существовавших

```powershell
node .\bin\selfreview.mjs review --config $srConfig --project a --base origin/main --merge-base --new-only --format json
node .\bin\selfreview.mjs review --config $srConfig --project a --staged --format json
node .\bin\selfreview.mjs review --config $srConfig --project a --staged --new-only --format json
```

Обычный `--base` сохраняет проверку затронутых узлов. `--merge-base` вычисляет и
записывает общего предка. `--staged` читает содержимое индекса Git, включая случаи,
когда рабочий файл отличается; по умолчанию база — `HEAD`. Внешний `--diff` с этим
режимом несовместим.

`--new-only` сравнивает полные изменённые файлы с доверенной локальной базой Git
и разделяет новые, существовавшие и устранённые находки. Дополнительные одинаковые
вхождения учитываются. Ухудшение уже нарушенной метрики размера/параметров считается
новой находкой с `baselineChange: "worsened"` и `previousMetric`. Одинаковое имя
функции у разных лексических владельцев не означает одну и ту же находку.
Произвольный переданный diff не доказывает состояние базы.
Отчёт сообщает способ сравнения и находки, влияющие на код завершения.

Для узкой проверки только новых нарушений нужна совместимая версия политики в
Git. Изменённая, незарегистрированная в Git или внешняя конфигурация/каталог могут
привести к явно обозначенной полной проверке. Это относится и к общей внешней
конфигурации из начала руководства: она поддерживается, но её прежнюю политику
нельзя восстановить из репозитория, в котором её никогда не было. Ошибка разбора
или чтения базового кода остаётся неполным анализом.

Изменение только README либо удаление файлов может дать `NOT_APPLICABLE`, что
не означает одобрения всего MR. Недоступный выбранный исходник и ошибка разбора
по-прежнему дают `INCOMPLETE`. Бинарные patch, в том числе изменения только бинарных
assets, пока не поддержаны и остаются неполным анализом. Ручное ревью, сборка, типизация и runtime-проверки
остаются отдельными этапами.

Контракты и проверка описаны в [WORKFLOW.md](docs/WORKFLOW.md) и
[плане реализации](IMPLEMENTATION_PLAN.md). Экономия времени человека и снижение

## Архитектурные источники

AST-адаптер использует TypeScript Compiler API; ESLint-адаптер оформлен как локальный plugin/flat config. Эти документы описывают механизмы интеграции, а не подтверждают качество конкретного набора конвенций:

- [Microsoft TypeScript: Using the Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)
- [ESLint: Custom Rules](https://eslint.org/docs/latest/extend/custom-rules)
- [ESLint: Configure Plugins](https://eslint.org/docs/latest/use/configure/plugins)

Описание декларативных правил, вариантов, исключений и источников: [RULES.md](docs/RULES.md).
